# Dataset Tool v1.2.0 Plan

Source: `.agent-workspace/dataset-tool-roadmap.md`

Current released project version appears to be `v1.1.0`. This plan targets
`v1.2.0` because the requested work is a set of backward-compatible CLI
features if defaults are preserved.

## Brutal Summary

The requested order is risky.

The original roadmap correctly puts PR5 last because mask label support is the
largest and least defined feature. Moving PR5 first is acceptable only if it is
treated as a design-locking PR, not as a casual implementation PR.

If PR5 is vague, PR3 and PR4 will inherit bad assumptions and the version will
ship a brittle dataset generator with a nicer CLI. That is worse than shipping
nothing.

## PR Order

## PR5: Segmentation/Mask Label Support

Goal:

- Add `--label-format bbox|mask`.
- Keep `bbox` as the default.
- Define exactly what `mask` means before writing implementation code.

Required decision:

- `mask` must mean YOLO segmentation polygon labels for `v1.2.0`.
- Do not use `mask` to mean copied `.npy` masks, PNG masks, or COCO JSON.
- If YOLO polygon output is not feasible now, PR5 must stop at a documented
  design decision and should not pretend to implement mask labels.

Acceptance gates:

- Existing bbox output is unchanged by default.
- Simple synthetic masks produce deterministic YOLO segmentation labels.
- Empty or invalid masks fail or skip with explicit accounting.
- Multi-object behavior is documented and tested.
- `data.yaml` remains valid for bbox and mask modes.
- Docs state that `.npy` masks are the input source.

Hard no:

- No silent fallback from `mask` to `bbox`.
- No ambiguous "mask label" files with undocumented format.
- No mixing COCO, copied masks, and YOLO segmentation in one PR.

Risk:

- High. This PR defines the dataset contract. If it is sloppy, every later PR
  compounds the damage.

## PR3: Raw Dataset Subsampling

Goal:

- Add deterministic raw-data sampling before splitting.
- Prefer `--sample-ratio`; add `--sample-count` only if the UX and validation
  are clean.
- Keep `--seed` as the deterministic control.

Acceptance gates:

- Sampling happens before train/val split.
- Same seed, same selected samples.
- Different seed can change selected samples.
- Invalid ratios fail clearly.
- Sampling behavior is identical for `bbox` and `mask` label formats.
- The selected sample list is testable and, ideally, written to a manifest.

Hard no:

- No sampling after split.
- No nondeterministic filesystem-order dependence.
- No partial sample generation where images exist without valid labels.

Risk:

- Medium. The implementation is straightforward, but reproducibility mistakes
  are easy and expensive.

## PR4: Copy/Symlink Mode

Goal:

- Add `--image-mode symlink|copy`.
- Default to `symlink` to preserve current behavior.

Acceptance gates:

- `symlink` preserves current output behavior.
- `copy` creates real files.
- Existing outputs are handled deliberately.
- Tests cover both modes where the platform supports symlinks.

Hard no:

- No default behavior change.
- No silent copy when symlink fails unless the user explicitly requested it.
- No destructive overwrite behavior without a clear policy.

Risk:

- Low. This is small, but it touches filesystem behavior, so sloppy edge cases
  can still damage user data.

## Version Gate

Ship `v1.2.0` only if all three PRs meet these conditions:

- Defaults preserve `v1.1.0` behavior.
- `bbox` output remains backward compatible.
- `mask` output format is documented and tested.
- Sampling is deterministic and happens before splitting.
- Copy/symlink behavior is explicit and tested.
- CLI help text no longer implies PNG masks are supported inputs.

If any default output layout changes, this is not `v1.2.0`; it becomes a major
version candidate.

## Final Call

Do PR5 first only if the team is ready to make the label-format decision now.

If that decision is not settled, the honest plan is:

1. PR5 design-only decision.
2. PR3 deterministic subsampling.
3. PR4 copy/symlink mode.

Trying to implement PR5 without locking the format is the highest-risk path and
should be rejected.
