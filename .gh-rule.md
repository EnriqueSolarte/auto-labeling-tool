# GitHub Repository Rules

This file defines how anybody should commit, version, tag, open PRs, and push changes for this repository. 
This file must read before changing Git state.

## Repository Identity

- Repository purpose: RGB autolabeling utilities for creating SAM2-assisted
  masks and YOLO training datasets.
- Default branch: `main`.
- Current working branch policy may use `dev` or feature branches before merge.
- Primary remote: `origin`.

## Branch Policy

- Protected branches: `main`.
- Direct pushes allowed to: feature branches and `dev`.
- Direct pushes to `main`: not allowed unless the user explicitly approves and
  confirms that the branch protection/review policy permits it.
- Feature branch naming: `type/short-description`, for example
  `docs/release-checklist` or `fix/docker-build`.
- If currently on `main`: create a feature branch before committing unless the
  user explicitly asks for a direct release commit.

## Commit Policy

- Commit message style: Conventional Commits.
- Commit scope rules: one logical change per commit; keep unrelated dirty work
  out of commits.
- Files that must not be committed: local `.env` files, generated datasets,
  local masks, model weights, caches, virtual environments, and machine-specific
  paths unless explicitly requested.
- Generated files policy: commit generated artifacts only when they are small,
  intentional release assets or documentation outputs.

## Conventional Commit Type Prefixes

- `feat:` new user-facing or developer-facing capability; usually MINOR.
- `fix:` bug fix; usually PATCH.
- `build:` build system, dependency, packaging, Dockerfile, compiler, or
  artifact-generation change.
- `ci:` continuous integration workflow, hosted check, or release automation
  change.
- `docs:` documentation-only change.
- `style:` formatting-only change with no behavior impact.
- `refactor:` code restructuring with no intended behavior change.
- `perf:` performance improvement.
- `test:` tests, fixtures, or test-only helper changes.
- `chore:` repository maintenance that does not fit a more specific type.
- `revert:` reversal of a previous commit.
- `type!:` or `BREAKING CHANGE:` incompatible API, CLI, data format, build,
  deployment, or workflow change; usually MAJOR.

Prefer the most specific prefix. For example, use `ci:` for hosted workflow
changes and `build:` for Docker changes instead of `chore:`.

## Checks Before Commit Or Push

- Required quick check when Python scripts change:
  `python3 -m py_compile` on the touched Python scripts, or on the main script
  set when preparing a release.
- Required Docker check when Docker files change: run the relevant Docker build
  command, or report clearly if it cannot be run in the current environment.
- Required documentation check when release docs change: verify referenced files
  and commands exist or are explicitly marked as future/TODO.
- If no automated tests exist: use syntax checks plus focused smoke/manual
  checks appropriate to the changed scripts.
- If checks fail: stop, report the failure, and do not push unless the user
  explicitly overrides.

## Versioning

- Initial version: `v0.1.0`.
- Version source of truth: `VERSION`.
- Version format: `vMAJOR.MINOR.PATCH`.
- Version bump required only when the user explicitly asks for a version bump,
  tag, release, or versioned change.
- Changelog or release notes required for versioned releases. For `v0.1.0`, a
  concise release checklist and known-issues notes are acceptable.

## Tags And Releases

- Tags required: yes, for versioned releases only.
- Tag type: annotated Git tags.
- Tag format: `vX.Y.Z`, matching `VERSION`.
- When to create tags: after release checks pass and the release commit is ready.
- Tags may be pushed only after user approval.
- Release creation policy: do not publish hosted releases unless the user
  explicitly requests it.

## Pull Request Policy

- PR required before merge to `main` unless the user explicitly approves a
  direct release commit.
- PR target branch: `main`.
- PR title format: Conventional Commit style when possible.
- PR body requirements: summarize changes, checks run, release/version impact,
  and known risks.
- Review requirements: follow the remote repository policy; if unknown, ask
  before merging or pushing directly to `main`.

## Push Policy

- Allowed push flow: commit on `dev` or a feature branch, push that branch, then
  open a PR to `main` when appropriate.
- Direct push allowed: yes for `dev` and feature branches.
- Force push allowed: no, unless the user explicitly confirms the exact branch
  and reason.
- Push tags allowed: yes only for approved versioned releases.

## Approval Requirements

Codex must ask before:

- pushing to `main`
- force pushing
- creating, deleting, or pushing tags
- publishing releases
- changing version numbers
- committing files outside the requested scope
- running destructive commands

## Reporting Requirements

After completing a commit, tag, push, or PR workflow, Codex must report:

- files committed
- checks run and results
- commit SHA
- branch pushed
- tags created or pushed
- PR URL, if created
